# CCR Architecture

This document explains how CCR is structured and how to modify it safely. For user-facing commands, see [commands.md](commands.md). For shared runtime terminology, see [glossary.md](glossary.md). For the current change summary, see [release-notes.md](release-notes.md).

## High-Level Shape

CCR is intentionally packaged as a single installer script:

- [`../ccr.sh`](../ccr.sh) is the source of truth (it expands the bin wrappers, slash commands, and config as heredocs).
- Running `bash ccr.sh` writes generated files into `~/.local/bin` and `~/.claude/commands`.
- The generated runtime is `~/.local/bin/ccr-cli.js`, a single dependency-inlined Bun bundle built from [`../src/cli.ts`](../src/cli.ts). It is NOT embedded inline in `ccr.sh`; it ships as the committed file [`../templates/bin/ccr-cli.js`](../templates/bin/ccr-cli.js) and `ccr.sh` installs it by copying that file from its own repo checkout (so `ccr.sh` stays small and the bundle is not duplicated).
- Shell wrappers such as `ccr-status`, `ccr-ready`, and `ccr-support` call `bun ccr-cli.js --command ...`.
- Claude and Codex hook configuration is merged into `~/.claude/settings.json` and `~/.codex/hooks.json`.

The runtime is authored as TypeScript under [`../src/`](../src) (`src/cli.ts`, `src/lib/*`, `src/commands/*`); `bun run build:cli` bundles it into `templates/bin/ccr-cli.js`. Integrity is guarded by `bundle-sync.test.ts` (committed bundle == a fresh `src/cli.ts` build) and `check:sync` (the 43 heredoc templates == `ccr.sh`). `bash ccr.sh` only requires `bun` — there is no Python at install or runtime.

## Generated Components

| Component | Generated Location | Purpose |
|---|---|---|
| `ccr-cli.js` | `~/.local/bin/ccr-cli.js` | Main Bun runtime bundle for hook events and shell commands (built from `src/cli.ts`). |
| `ccr-lib.sh` | `~/.local/bin/ccr-lib.sh` | cmux workspace/surface helpers used by setup commands. |
| `ccr-hook-claude` | `~/.local/bin/ccr-hook-claude` | Claude hook entry wrapper. |
| `ccr-hook-codex` | `~/.local/bin/ccr-hook-codex` | Codex hook entry wrapper. |
| `cmux-setup-claude` | `~/.local/bin/cmux-setup-claude` | Registers the current surface as Claude and launches Claude Code. |
| `cmux-setup-codex` | `~/.local/bin/cmux-setup-codex` | Registers the current surface as Codex and launches Codex. |
| `ccr-*` commands | `~/.local/bin/ccr-*` | User commands that delegate to `bun ccr-cli.js --command`. |
| Claude slash commands | `~/.claude/commands/ccr-*.md` | Claude-side command helpers. |

The generated command registries live in [`../src/lib/constants.ts`](../src/lib/constants.ts) (bundled into `ccr-cli.js`):

- `GENERATED_BIN_NAMES`
- `GENERATED_CLAUDE_COMMAND_FILES`

Keep these aligned with wrapper generation (the `ccr.sh` heredocs), `ccr-doctor`, `ccr-uninstall`, and documentation.

## Runtime State

Repository-local state lives under:

```text
<repo>/.cmux/ccr/
```

Important files:

| Path | Purpose |
|---|---|
| `state.json` | Loop state: `review_count`, `last_diff_hash`, `active_request`, latest completed round. |
| `status.json` | Human-readable status plus latest report pointer. |
| `events.jsonl` | Operational event log consumed by `ccr-events` and support bundles. |
| `skip-next.json` | One-shot marker consumed by the next eligible automatic review. |
| `sessions/<sid>/rounds/<n>/request.md` | Review request sent to the opposite agent. |
| `sessions/<sid>/rounds/<n>/diff.patch` | Diff payload reviewed in that round. |
| `sessions/<sid>/rounds/<n>/delta.patch` | Round-to-round diff when available. |
| `sessions/<sid>/rounds/<n>/worker-followup.md` | Worker's follow-up text for later rounds. |
| `sessions/<sid>/rounds/<n>/review.md` | Reviewer response. |
| `sessions/<sid>/rounds/<n>/decision.json` | Parsed review decision and metadata. |
| `sessions/<sid>/report.md` | Session report generated by terminal states or `ccr-report`. |
| `support/ccr-support-*.zip` | Diagnostic support bundles. |

State writes use `locked_state()` to avoid concurrent hook updates.

## Hook Event Flow

`handle_hook()` receives hook JSON from Claude or Codex wrappers.

Main paths:

1. `SessionStart`
   - initializes local status as idle.
2. `UserPromptSubmit`
   - resets round counters only when no review is active.
   - ignores CCR handoff sentinel prompts.
3. `PreToolUse`
   - blocks mutating tools while the current agent is reviewer.
4. `PostToolUse`
   - marks the session dirty only for mutating tools or mutating-looking Bash.
5. `Stop`
   - reviewer stop finalizes a review via `finish_review()`.
   - worker stop may create a review via `start_review()`.

## Review Start Flow

`start_review()` is the automatic review gate.

It checks:

- dirty marker exists,
- no active review request exists,
- max rounds not exceeded,
- current cwd is a git worktree,
- collected diff has content,
- diff meets `CCR_MIN_DIFF_LINES`,
- diff hash differs from the last reviewed diff,
- `ccr-skip-next` is not pending,
- the prompt gate does not suppress it (`CCR_PROMPT_GATE=on`): the developer did not emit `CCR_REVIEW: skip`, and (when no `CCR_REVIEW: request` overrides) the user prompt was not classified read-only. This step is suppress-only — it can drop an otherwise-eligible review but never starts one.

If eligible, it writes round artifacts and sends a handoff message to the opposite cmux surface.

`ccr-preview` mirrors much of this logic without mutating state.

## Review Finish Flow

`finish_review()` parses the reviewer response and routes based on:

- `PASS`: clears active request and generates a report.
- `NEEDS_CHANGES`: sends the review path back to the worker.
- `NEEDS_HUMAN`: stops for user judgment and generates a report.
- invalid/missing decision: stops for manual intervention.

Decision parsing ignores fenced examples and blockquotes so examples do not accidentally become the verdict.

## Reports And Support

`generate_session_report()` creates `report.md` for terminal loop states and manual regeneration.

`ccr-support` creates a zip with:

- `doctor.json`,
- version information,
- state/status,
- event tail,
- latest session metadata.

It excludes request, review, and diff payloads by default. Payloads require `--include-diffs`.

## Self-Tests

There are two self-test surfaces:

- installer-time self-test inside `bash ccr.sh`,
- runtime `ccr-selftest`.

They cover core parser behavior, dirty filtering, prompt reset safety, diff truncation, doctor/ready/support JSON, preview, prune, config, and events.

Run after code changes:

```sh
bash -n ccr.sh
ccr-selftest
```

For install-generation changes, run an isolated install as shown in [validation.md](validation.md).

## Adding A New User Command

When adding a `ccr-*` command, update all relevant places:

1. Add the command implementation under `src/commands/` (and any shared logic in `src/lib/`).
2. Add the command to the arg parser (`src/lib/args.ts`) and dispatch it in `src/cli.ts`.
3. Add a shell wrapper heredoc under `cat > "$BIN_ROOT/..."` in `ccr.sh` (`exec bun "$HOME/.local/bin/ccr-cli.js" --command ...`).
4. Add the command to `GENERATED_BIN_NAMES` in `src/lib/constants.ts`.
5. Add uninstall coverage through the generated registry.
6. Add `ccr-doctor` coverage through the generated registry.
7. Add a Claude slash command when useful.
8. Add the slash command file to `GENERATED_CLAUDE_COMMAND_FILES`.
9. Add self-test coverage in `src/commands/selftest.ts` if behavior is nontrivial.
10. Run `bun run build:cli` to rebuild `templates/bin/ccr-cli.js`; if you edited a `ccr.sh` heredoc, run `bun run extract:templates`; verify with `bun run check:sync`.
11. Update `README.md`, [commands.md](commands.md), [examples.md](examples.md), and [index.md](index.md).
12. Update [automation.md](automation.md), [troubleshooting.md](troubleshooting.md), [rollout.md](rollout.md), or [templates.md](templates.md) when the command affects those workflows.
13. Update `ccr-help` when the change creates or changes a user-facing docs entry point.
14. Run the documentation checks from [validation.md](validation.md) when docs, templates, or help text changed.

## Design Constraints

- Keep install-time dependencies minimal; currently only `bun` is required.
- Prefer JSON output for automation-capable diagnostics.
- Default destructive operations to dry-run (`ccr-prune`, `ccr-uninstall`).
- Do not include request/review/diff payloads in support bundles unless explicitly requested.
- Keep reviewer-only mutation blocking conservative.
- Keep docs and generated command registries aligned.
